The puzzle and the run

What this project solves, and what happens in the seconds after you press Enter.

A delivery driver with 52 stops

Picture a courier in Berlin with 52 parcels. They must visit every address once and end up back at the depot, driving as little as possible. That is the Travelling Salesman Problem, and this project is a program that tackles it.

📍

52 cities

The main test map is called berlin52. Each city is just a pair of x and y coordinates in a text file.

♾️

About 7.8 × 1065 routes

That is how many different round trips exist for 52 cities. No computer can check them all.

🏁

7542

The shortest possible berlin52 route, proven by researchers. It is the target every run is measured against.

The trick: breed routes instead of checking them

Since checking every route is impossible, the program borrows an idea from nature. It keeps a crowd of candidate routes and lets the good ones have "children". This approach is called a genetic algorithm.

Good enough, fast

A method that finds a very good answer quickly, without promising the perfect one, is called a heuristic. Much real software works this way, from map directions to delivery scheduling. When you ask an AI tool for an "optimal" solution to a huge problem, a heuristic is usually what you should expect back.

03

One generation, up close

Select, mix, tweak. The three moves that repeat 500 times, and the three settings that control them.

A gardener saving seeds

A gardener who wants sweeter tomatoes keeps some of this year's plants, crosses the best ones to get seedlings, and accepts that a few seedlings will turn out odd. Next year they do it again. One round of that is a generation, and the whole crowd of 100 routes is the population.

30 kept
70 children (35 pairs of parents, 2 children each)

That split comes from one setting, the replacement rate, which defaults to 0.7. This is the arithmetic in ga.py.

CODE 
    num_pairs = round(r * p / 2)
    num_children = 2 * num_pairs
    keep_n = p - num_children

    assert keep_n >= 0

    return keep_n, num_pairs
PLAIN ENGLISH

How many pairs of parents do we need? Take the replacement share of the population and halve it. With 0.7 and 100 that is 35.

Each pair makes two children, so 70 children.

Whatever is left over is carried into the next generation: 30.

Safety check: that leftover number can never be negative.

Hand both numbers back to whoever asked.

Move 1: pick a parent with a mini-contest

To choose a parent, the program draws five routes at random and takes the shortest of the five. This is called tournament selection.

CODE 
    # Pick k random indices
    indices = [rng.randrange(len(costs)) for _ in range(k)]
    
    # Return the index with the lowest cost
    return min(indices, key=lambda i: costs[i])
PLAIN ENGLISH

A note: choose k contestants.

Draw k random position numbers from the population. With the default settings, k is 5.

A note: the shortest route wins.

Of those contestants, hand back the position of the one whose route is shortest.

💡
Selection pressure

The contest size is a dial. A bigger contest means the very best routes win almost every time, so the crowd improves fast but soon all looks alike. A smaller contest gives weaker routes a chance and keeps variety alive. Engineers call this dial "selection pressure".

Move 2: mix two routes without breaking them

A route must contain every city exactly once. Gluing half of one route to half of another would repeat some cities and drop others. The mixing method here, order crossover, avoids that.

Parent A 0 1 2 3 4 5 6 7
Parent B 3 7 0 5 1 6 2 4
Child 5 1 2 3 4 6 7 0

The teal stretch (2, 3, 4) is copied straight from Parent A. Parent B then supplies the rest in its own order, starting after the stretch and wrapping around: 6, 7, 0, 5, 1. Cities already used are skipped.

CODE 
    child = [None] * n
    child[cut1:cut2+1] = p1[cut1:cut2+1]
    
    used= set(child[cut1:cut2+1])
    
    fill=[]
    for city in p2[cut2+1:] + p2[:cut2+1]:
        if city not in used:
            fill.append(city)
PLAIN ENGLISH

Start the child as a row of empty slots, one per city.

Copy the stretch between the two cut points from the first parent into the same slots.

Remember which cities are now taken.

Start an empty waiting list.

Walk through the second parent, beginning just after the stretch and wrapping around to the front.

If a city is not already taken…

…add it to the waiting list. The list then fills the empty slots in order.

Move 3: a small random tweak

Mixing only reshuffles what the crowd already has. A mutation introduces something new. The project has two kinds, and a setting chooses between them.

Swap

Two cities trade places.

Up to four roads in the route change.

↩️

Inversion

A stretch is driven in reverse.

0 1 5 4 3 2 6 7

📝
Why the default is inversion

The settings table in experiments.py chooses inversion, and a note beside it records why: on berlin52 with random starting routes, inversion finished about 8.4% from the best possible route against about 24.8% for swap.

The three moves, assembled

This is the heart of ga.py, the part that runs once per generation. A loop appears three times: once to keep, once to breed, once to tweak.

CODE 
        # Survivors: keep_n = (1-r)p picked by tournament selection
        new_population = []
        for _ in range(keep_n):
            i = tournament_selection(costs, k, rng)
            new_population.append(population[i][:])

        # Create children using crossover
        for _ in range(num_pairs):
            i = tournament_selection(costs, k, rng)
            j = tournament_selection(costs, k, rng)

            child1 = order_crossover(population[i], population[j], rng)
            child2 = order_crossover(population[j], population[i], rng)

            new_population.append(child1)
            new_population.append(child2)

        # Mutate a fixed number of individuals
        positions = rng.sample(range(p), num_mutants)

        for i in positions:
            new_population[i] = mutation_fn(new_population[i], rng)
PLAIN ENGLISH

Start next year's crowd as an empty list.

30 times: hold a mini-contest and carry a copy of the winner forward. The same strong route can win more than once.

35 times: hold two mini-contests to find two parents.

Mix them twice, swapping which parent donates the copied stretch, to get two different children.

Add both children to next year's crowd.

Choose 10 positions at random out of the 100. That is the mutation rate of 0.1.

Replace each chosen route with a tweaked copy of itself. Any route can be chosen, including the best one.

Three dials to steer with

k = 5 Contest size. Higher favours the best routes more strongly.
r = 0.7 Replacement rate. Higher means more children and fewer routes carried over.
m = 0.1 Mutation rate. Higher means more random tweaks per generation.

A head start

Where the first 100 routes come from, two speed tricks worth knowing by name, and a trap that hides your results.

Sea level or base camp?

A climber can start at the coast or get a lift to base camp. Evolution works either way, but the starting point decides how much climbing is left. The scout file offers four starting points.

🎲

random

Shuffle the cities 100 times. Awful routes, maximum variety.

🧲

nn

Always drive to the closest unvisited city, then tidy up the route.

🧭

angle

Stand in the middle of the map and visit cities in the order a clock hand would sweep past them.

🧠

smart

Half the crowd from nn, half from angle.

Nearest neighbour: always take the closest

This is a greedy method. It never looks ahead, so the last few cities are often far apart.

CODE 
    while not_visited:
        current = tour[-1]
        row = dist_matrix[current]
        nearest = min(not_visited, key=lambda city: row[city])
        tour.append(nearest)
        not_visited.remove(nearest)
PLAIN ENGLISH

Keep going while any city is still unvisited.

Where are we now? The last city on the route so far.

Open the distance table at the row for this city.

Among the unvisited cities, find the one with the smallest distance in that row.

Drive there: add it to the end of the route.

Cross it off the unvisited list.

Tidying up: uncross the roads

If two legs of a route cross each other, there is always a shorter way to connect the same four cities. The tidy-up step, called 2-opt, hunts for those and fixes them.

Before: a to b, and c to d

After: a to c, and b to d

PLAIN ENGLISH

We already hold one road, from a to b. Now try every later road in the route as its partner.

That later road runs from c…

…to d. The "% n" wraps around, so the road after the last city leads back to the first.

Are the two current roads longer, added together, than the two roads we would get by reconnecting?

If so, reverse the stretch between them, which performs the reconnection.

Note that we found an improvement.

Stop scanning and start the search again from the top.

💡
Only measure what changed

The check compares four roads. It does not re-measure the whole route, because every other road stays the same. Engineers call this "delta evaluation". The project's README credits it with cutting a test run from about 20 seconds to about 0.2.

Work it out once, look it up forever

The D[a][b] lookups above read from a distance matrix. Storing answers so you never compute them twice is called caching. For 200 cities one table holds 40,000 distances.

Here the scout builds routes for the "nn" starting method. Look at what each call is given.

PLAIN ENGLISH

If the chosen starting method is "nn"…

…do the following once for each of the 100 routes we need.

Build a nearest-neighbour route. The starting city cycles through the cities: 0, 1, 2… and back to 0 when they run out.

🔍
A missed lookup table

Neither call is handed a ready-made distance table, so each one builds its own: 200 tables for 100 routes. The "smart" method in initialization.py builds the table once and passes it along. I have not timed how much this costs, but it is repeated work, and it is the kind of thing you can now spot and ask an AI tool to fix: "build the distance matrix once and pass it in."

⚠️
The ceiling trap

If the starting routes are already at or near perfect, the genetic algorithm has nothing left to improve, and every setting looks equally good. The code says so itself: experiments on settings default to random starts "to avoid smart ceiling". When you measure a change, make sure there is room for the measurement to move.

Can you trust the numbers?

Luck is built into this program. Here is how the code keeps luck under control, and where its own notes have drifted from the truth.

A world seed for randomness

In a world-building game, typing the same world seed gives every player the same mountains and rivers. Computer randomness works the same way. A seed fixes every "random" choice that follows.

    def cost_fn(tour, D):
        return calculate_cost(tour, D, weight_type)

Prepare the "make me starting routes" tool for the chosen starting method.

Prepare the "measure a route" tool…

💡
Reproducibility

If you cannot repeat a run exactly, you cannot tell whether a change you made helped or you just got lucky. Being able to repeat it is called reproducibility, and it is the first thing to ask for in any program that uses randomness.

Parts that plug in

The breeder does not make its own randomness, starting routes or measurements. All three are handed to it from outside. Engineers call this dependency injection.

rng The seeded source of random numbers. Swap the seed, get a different but repeatable run.
init_fn The "make starting routes" tool. Swap it to compare random, nn, angle and smart.
cost_fn The "measure a route" tool. Swap it to change the distance rule, or to plug in a fake one for testing.
params The dials: population size, replacement rate, mutation rate, generations, contest size.

One knob at a time, many runs each

With the default settings and random starts on berlin52, 30 runs that differed only in their seed finished anywhere from 7934 to 8731. That is a gap of 5% to 16% from luck alone, so a single run proves very little.

1
Change one setting

For example population size: 50, 100, 120, 150. Everything else stays at its default.

2
Repeat each value several times

Every repeat gets its own seed, worked out from the master seed you typed.

3
Write every run down

One line per run in a results file: map, setting, seed, final length, starting length, gap, time.

4
Compare averages

The charts plot the average progress across the repeats, so one lucky run cannot mislead you.

    for method in INIT_METHODS:
